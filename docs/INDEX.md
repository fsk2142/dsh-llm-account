# 文档索引

按**主题**组织。改代码之前先在这里找对应文档。

| 文档 | 讲什么 | 什么时候读 |
| --- | --- | --- |
| [SPEC.md](SPEC.md) | 设计规格：架构、契约、切换策略、界面结构（**唯一权威**） | 改设计、判断「该不该这样做」 |
| [vendors.md](vendors.md) | 三家网关的**当前有效**事实：端点、认证、配额形状、窗口口径 | 改适配器、加厂商、排查上游报错 |

| [reviews/](reviews/) | 独立代码审查报告 | 想知道「这一轮查过什么」 |

## 约定

- **SPEC 是权威**：实现与它冲突时以它为准，要改先改它。
- **operations 是手册**：每节以症状开头，先找症状再走证据链。
- **decisions 的编号不可改**：代码里有 30 处注释按编号引用它（7 个编号：1/2/16/19/22/23/34）。
  新增裁决继续往后编号。
- **history 只记录，不作为依据**：需要结论时看上面几份。
- **提交信息带 `feat:`/`fix:`/`chore:` 前缀**：版本号靠它自动推导（见 RELEASING.md）。

## 关于「历史结论会过时」

文档里的**测试数量、行号、当时的数据**都只反映写作那一刻，不要当成现状核对依据 ——
要准确数字就现跑（`npx vitest run`、`npx tsc --noEmit`）。

整理时遵循这一条（2026-10-22）：

- **vendors.md 只放当前有效的事实**，施工过程移进 history.md；
- 已失效但仍值得记住的**通用教训**（如「静态 import 可选依赖会让宿主起不来」）
  保留在原处并加「现状」说明，而不是直接删掉；
- 修文档时**顺手核对引用**：文档里写的 `src/...` 路径必须真实存在
  （本次修掉 11 处失效路径）。
