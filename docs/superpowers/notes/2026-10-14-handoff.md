## 2. 工作流程（本仓库固定用法）

superpowers 的 **subagent-driven-development（SDD）**，逐任务闭环：

```
写 brief（<workspace>/task-N-brief.md）
→ 实现者 TDD：写失败测试 → 跑到失败 → 实现 → 跑到通过 → 提交 → 自审 → 写 task-N-report.md
→ 控制器出 review package（git log/diff 重定向到文件：review-task-N.md）
→ 任务复核（独立子代理；**若用户要求「自己干」，则控制器本人复核并如实记录独立性变弱**）
→ 有 Critical/Important → 修复轮 → 复审通过
→ 下一个任务
→ 全部完成后：一次全分支复核 → 收尾
```

**本会话的用户约束**：`自己干，不准派子智能体` —— 控制器同时是执行者与复核者，**独立性弱于正常流程**，必须在报告与 ledger 里如实写明（T1–T4 都这么做了）。

## 5. 必须继承的「坑」与裁决（不读会重犯）

- **客户端接缝仍是未验证假设**（`host-seam-assumptions.md`），1c 才能真机验证。T1–T4 已把所有接缝收进 `src/client/shell.ts` 与 `src/client/seams.ts` 两层，**1c 只改这两层**。
- **cordis 的 `Service` 实例对外是代理**：`#` 私有成员会抛 `TypeError: Receiver must be an instance of class …`（T3 实测）；服务里一律用 TS `private`。
- **cordis 的服务解析只向上找**：两个 profile 行的注入作用域是**兄弟**，共享服务必须注册在 `ctx.root`（T3 实测）。
- **`ctx.set` 之前必须 `ctx.provide`**（cordis 4）。
- **宿主提供的包必须保持外部**：`@deepseek-ai/dsh-typert-protocol` 曾是 `devDependencies` 被**内联**（T3 实测），内联副本与宿主 Gateway 的基类不是同一类身份 → 已在 `peerDependencies` + `tsdown` 的 `neverBundle` 里钉住；构建测试断言「整目录里至少有一个产物仍裸导入它」。
- **客户端产物护栏**：`lib/client.js` 必须自包含（不相对引用分块）、裸导入必须只有宿主白名单（`react` 等）、`node:` 命中 0。
- **浏览器产物里绝不能出现 `node:*`**。
- **`inject` 必须写 cordis 服务名**（`slots`/`locale`/`remote`），不是 npm 包 id；读 `ctx.remote.credentials` 前必须先注入。
- **厂商识别**：只有一个 `./client`，两行都加载它 → 靠**设置命名空间发现**厂商（Ruling 2）。**opencode 的宿主行 id（`opencode-go`）与核心命名空间（`llm-opencode-go`）不同**，注册表用 `rowIds` 两个都列（Ruling 25）。
- **`hooks` 映射**：目前注册的页面 `inject: () => ({ hooks: {} })` 是空对象（1a 的形状假设）；1c 要验证 `hooks` 键是否真的被投影成 `use<Key>`。
- **`unavailable` 不产出切换提示、不编造原因**（Ruling 17）。
- **额度读数只属于「当前选中的账号」**：发布摘要时必须显式给归属，不能挪到生效账号头上（T3 的 Ruling 19）。
- **意图日志的重放仍未接线**（1c 要加崩溃重放演练）；**登录 `storeKey` 的 ref 撞名处置**在 T5 Step 7。
