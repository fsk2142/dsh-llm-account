## 2. 工作流程（本仓库固定用法）

用的是 superpowers 的 **subagent-driven-development（SDD）**，逐任务闭环：

```
写 brief（<workspace>/task-N-brief.md，内含该任务全文 + Global Constraints + 控制器补充）
→ 派实现者子代理（新上下文，只给它 brief 路径）
→ 实现者 TDD：写失败测试 → 跑到失败 → 实现 → 跑到通过 → 提交 → 自审 → 写报告（task-N-report.md）
→ 控制器出 review package（git log/diff 重定向到文件）→ 派新子代理做任务复核
→ 有 Critical/Important → 修复轮（resume 原实现者）→ 限定范围复审
→ 通过 → 下一个任务
→ 全部完成后：一次全分支复核 → 收尾
```

### 硬规则（违反会造成真实事故，仓库里已经踩过）

- **禁止 `git commit --amend`**：控制器与子代理会并发提交，`--amend` 已经误吞过别人的提交一次。
- **禁止 `git checkout` / `git stash` / 任何可能回退未提交改动的命令**；要做变异检验就在仓库外的副本里做。
- **验证顺序是 `pnpm build && pnpm typecheck && pnpm test`**：`lib/` 被 gitignore，干净克隆下单独 `pnpm test` 会因缺 `lib/client.js` 而红（构建测试会给出可操作的提示）。
- **不要提交 `lib/`**。
- `src/core/**` 与 `src/vendors/**` 的第 1a 期成果**已复核冻结**；只有计划点名的地方可以改（本计划是 T2 改 `rotation.ts`、T3 改两个 entry 与适配器的成功回报）。
- **数值/额度缺失不得当作 0**；写 `visibleModels` 前丢弃空串与纯空白。
- **密钥只进凭据服务**；客户端只通过 `remote.credentials` 读写，绝不从设置文档读明文。
- 删除类操作走 `safe_delete`（移入回收站）；OS home 目录内的对象属「确认删除区」，需要用户显式批准（`dsh-safety allow <id>`），**不许绕行**。

### 子代理的「启动即死」问题

长任务派发**偶发**启动即死（上一期 5 次、本会话已数次）。最小探针（让它回 `ROUTE_OK`）与只读探针都正常，说明是那条具体派发的问题。处置流程：

1. 先看它死前是否留下了产物（文件可能已经写好，只是死在提交前）。
2. **产物已落盘** → 控制器自己跑 `pnpm build && pnpm typecheck && pnpm test` 验证，然后**原样**代为提交，提交正文里写明「实现者死亡、控制器验证并提交孤儿产物」。
3. **半成品**（编译不过 / 只改了一半）→ 控制器读完 diff 补完，再验证、提交，并在 ledger 记录。
4. 无论哪种，都要在 ledger 里记一条 Ruling。

- **客户端接缝仍是未验证假设**（`host-seam-assumptions.md`）：`window.__ModuleLoader__`、`settings.section`、`hooks`→`use*` 投影、插槽注册、`order`。因为本机没有与桌面端同版本的 `dsh` CLI（PATH 上是 0.1.1-rc.2，桌面端引擎是 0.2.0-rc.2），**真机验证只能等计划 1c（用户在场）**。做法：逐字对照两个旧插件已编译的客户端 bundle，把所有接缝收在 `src/client/shell.ts` 一层里。
- **客户端 `inject` 必须写 cordis 服务名**（如 `slots`/`locale`/`remote`），**不是** `package.json` 里的 npm 包 id —— 两者本来就不同。读 `ctx.remote.credentials` 前**必须先注入** `remote.credentials`（可顶层可嵌套；`@mars-sea/dsh-commandcode-provider/lib/client.js:7764` 是嵌套写法，`dsh-better-sidebar/lib/client.js:29458` 把点号子服务写在顶层）。

- **`exports["./client"].types` 指向未产出的 `lib/client.d.ts`**（1a 遗留悬空指针）——裁决是**去掉该类型条件**，这件事安排在 T1。
