## 1. 这是什么

一个 **DSH 插件包**（`package.json` 的 `name: dsh-llm-account`），把两个厂商的**多账号**统一到一个账号中心：

| 厂商 | provider 路由 id | 设置命名空间 | profile 行 id |
| --- | --- | --- | --- |
| Command Code | `commandcode` | `llm-commandcode` | `llm-commandcode` |
| OpenCode Go | `dsh-opencode-go` | `llm-opencode-go` | **`opencode-go`**（≠ 命名空间，见 §7） |

一个包、两个子路径入口（`dsh-llm-account/commandcode`、`/opencode`）各装一行，外加**一个客户端 bundle**（`./client`）被两行共享。

分三期：**1a 宿主侧**（内核 + 两厂商适配器 + 两行装配，完成）、**1b 客户端**（统一页面 / 侧边栏卡片 / 仪表盘，完成）、**1c 真机验收**（待做，需要你在场）。

### 5.1 数据流（一次请求看谁在服务）

```
请求 → 适配器 rotation.pick()（内核；命中即记「生效账号」）
     → 请求成功 → rotation.noteSettled(ref)（把生效账号修正为最近成功者）

宿主侧 → usage-remote.status(vendor) 发布 { effective, pinned, switch, accounts[{quota, rejection}], capabilities }
客户端 → seams.mountUsageRemote（$mount + inject(["remote.llm-account"])）→ 各卡片渲染
```

## 6. 关键机制（读代码前必读）

- **生效账号是一等概念**（规格 §8.1）：`rotation.ts` 在每次 `pick` 命中时记录 `{ref, at}`，请求成功后由 `noteSettled` 修正为「最近成功者」；切换原因只有四种能被**指名**（额度耗尽/限流/凭据失效/手动），`unavailable` 只更新账号、**不编造原因**（Ruling 17）。引擎在账号库变化时会被重建，重建时**必须连同观测状态一起搬**（`adoptObservations`，Ruling 16）。
- **远程面只有一个**：cordis 服务键 `llmAccountUsage`，线上命名空间 `llm-account`（客户端侧预期服务名 `remote.llm-account`，**未在真机验证**）。方法 11 个：`status`/`accounts`/`switches` + `addAccount`/`renameAccount`/`replaceKey`/`removeAccount`/`selectAccount`/`moveAccount`/`setAutoSwitch` + `loginBegin`/`loginStatus`/`loginCancel`。**两侧描述符出自同一份契约**（`src/client/usage-contract.ts`），不许各写一份。
- **能力声明只在宿主侧**：两个 entry 各自声明 `VendorCapabilities`（规格 §7.3），经 `status().capabilities` 发布；客户端据此隐藏/置灰控件（`reorder`→移动控件、`pin`→固定项、`browserLogin`→登录入口、`modelVisibilityWrite`→保存后生效/立即生效）。**客户端不许再抄一份**（Ruling 28）。
- **厂商声明的三个可选字段是「这家支持什么」的唯一来源**（Ruling 25/33）：`rowIds`（宿主行名候选，opencode 行 id ≠ 命名空间）、`cards`（通用字段卡片）、`models`（模型可见性）。**缺席 = 不渲染/不发现**。
- **额度诚实**：`src/client/quota.ts` 是唯一实现 —— `used`+`cap` 齐才写 `x/y`，`percent` 有才写百分比，都没有显示「暂无额度数据」；**真的 0/0 照原样显示**。四张卡片全部走它（分支级变异验证过：改坏这一处四处同时报红）。
- **密钥路径**：客户端 → 远程 `replaceKey`/`addAccount` → 宿主**账号端口** → **凭据服务**。密钥永不进设置文档、不进日志、不回显（卡片里密钥输入框刻意不带 `data-field`，因此进不了设置草稿与保存条）。**没有**走旧插件的 `remote.credentials` 直写路径（Ruling 41 记录了这个解释）。
- **侧边栏开关与门控**（2026-10-15 改写，Ruling 43/44）：插槽是**常驻注册**的（apply 期一次，`registerSharedSurfaces`），组件按**已存储**的开关自门控 —— 关闭 → 渲染 `null` + 停轮询 + 不注册 `visibilitychange`；开启才轮询（60 s）。开关存在**模块级存储**里，写者是插件级设置镜像（首读 + `settings/document-updated` 订阅，旧插件同事件名）与设置页容器（每次快照重读后）；冷启动（设置页从未打开）时卡片自己 describe 一次。**为什么不是「按开关条件注册」**：插槽服务不返回注销句柄，条件注册一旦开启就撤不下来（旧插件注释原话 "The entry stays REGISTERED — this is a render decision"）。**usage 远程面同样是插件级共享单例**（`ensureUsageRemote`，apply 期挂载，卸下后自愈重挂）—— 设置页关掉不该带走侧边栏卡片与仪表盘的数据源。
- **客户端设置写行名**（Ruling 45）：`saveSettings` 写 describe 命中的**行名**（`VendorSnapshot.row`），不是核心命名空间 —— 宿主按 profile 条目 id 寻址，opencode 的条目 id（`opencode-go`）与命名空间（`llm-opencode-go`）不同。
- **保存失败不静默**（Ruling 46）：`saveSettings` 返回 `undefined`（成功）或宿主给出的可读原因；保存条显示 `save.failed`；每次保存后重读宿主（不猜修订号）。
- **样式层**：`css.ts` 的样式表只用宿主 `--dsw-*` 变量（变量名逐个 grep 自已装插件），`injectPluginCss` 与旧插件同形（无 document → 空操作；同 `data-plugin-css` id → 空操作；否则建标签并返回移除器），在 `applyShell` 里注入一次（Ruling 42）。
- **两个入口各自关掉宿主自动表单**（`disableSettingsAutoForm`），否则宿主自动生成的表单会和统一页面并排出现。

## 7. 必须继承的坑（不读会重犯，全部有实测来源）

1. **cordis 的 `Service` 实例对外是代理**：`#` 私有成员会抛 `TypeError: Receiver must be an instance of class …`。服务类里一律用 TS `private`（T3 实测）。
2. **cordis 的服务解析只向上找**：两个 profile 行的注入作用域是**兄弟**，共享服务必须注册在 `ctx.root`；`ctx.set` 之前必须先 `ctx.provide`（T3 实测）。
3. **宿主提供的包必须保持外部**：`@deepseek-ai/dsh-typert-protocol` 曾是 `devDependencies` 而被**内联**，内联副本与宿主 Gateway 的基类不是同一类身份（只有真机能发现）→ 已进 `peerDependencies` + `tsdown` 的 `neverBundle`，并由构建测试断言「整目录里至少有一个产物仍裸导入它」（内联会消灭 specifier）。
4. **`devDependencies` 默认会被打进产物**（`dependencies`/`peerDependencies` 才是外部）—— 加任何宿主包前先想清楚。
5. **浏览器产物护栏**：`lib/client.js` 必须**自包含**（不相对引用分块）、裸导入只在白名单（`react` / `react/jsx-runtime` / `@deepseek-ai/dsh-client-ui-primitives`）、`node:` 命中 0。
6. **客户端 `inject` 写 cordis 服务名**（`slots`/`locale`/`remote`），不是 npm 包 id；读 `ctx.remote.credentials` 前必须先注入（Ruling 7/10）。
7. **厂商识别靠设置命名空间 + `rowIds`**：只有一个 `./client`，两行都加载它，**不能**靠实例身份判断厂商（Ruling 2）；opencode 的行 id 是 `opencode-go` 而命名空间是 `llm-opencode-go`（Ruling 25）。
8. **护栏也要用变异验证**：我自己在 T3 写的「客户端只引用白名单模块」正则曾对**正确代码**报违规（属性名 `data-switch-from` 里的 `from"` 被当成导入）。**假阳性比没有护栏更糟** —— 它会训练人忽略它。修完要用「反向变异」确认它仍然抓得住真违规。
9. **不能按「效果」断言**：T3 的成功路径测试原本断言「请求后生效账号 = 服务账号」，但 `pick()` 早就把它置好了 —— 去掉 `noteSettled` 测试照样绿。改成**观察调用本身**才有判别力。
10. **cordis 服务的注册是异步生效的**：`ctx.inject` 的回调下一个宏任务才跑（测试里要 `setTimeout(0)`）。
11. **`main` 插槽用 `key`，`settings.section` 与 `sidebar.footer.action` 用 `id`**（旧插件的两种形状，抄错会导致面板永远打不开）。
12. **测试环境没有 DOM**（`lib` 里也没有 DOM）：组件按「纯 props → 元素树」测，React 用测试替身（**Hook 一律抛错**，机械保证被测组件无状态）；`document` 一律窄化结构读取，不给工程加 `DOM`。

## 8. 工作流程与硬规则

### 8.1 本期用的流程（SDD 闭环）

```
写/读任务书 → 实现者 TDD（写失败测试 → 跑到失败 → 实现 → 跑到通过）→ 提交 → 自审 → 写 task-N-report.md
→ 控制器出 review package（git log/diff 重定向到 review-task-N.md）→ 任务复核
→ 有 Critical/Important → 修复轮（新提交，不 amend）→ 复审
→ 下一个任务 → 全部完成后：一次全分支复核
```

**本期偏差（如实记录）**：从 T2 起**没有单独写 `task-N-brief.md`**，任务要点直接落在 `task-N-report.md` 里；**用户要求「自己干，不派子智能体」**，因此控制器同时是执行者与复核者 —— **独立性弱于正常流程**，每个任务的报告与 ledger 都写明了这一点。

### 8.2 硬规则（违反会造成真实事故）

- **禁止 `git commit --amend`**；**禁止 `git checkout` / `git stash` / 任何可能回退未提交改动的命令**（本仓库因此踩过坑）。
- **验证顺序固定为 `pnpm build && pnpm typecheck && pnpm test`**：`lib/` 被 gitignore，干净克隆下单独 `pnpm test` 会因缺构建产物而红。
- **不要提交 `lib/`**。
- **变异检验（Ruling 15）**：工作树在该提交上干净时**允许在仓库内做**，但必须（a）用精确反向编辑还原、（b）还原后 `git diff --stat` 为空且全量复跑通过；`checkout`/`stash`/`--amend` 仍然禁止。
- **删除一律走 `safe_delete`**（移入回收站，可 undo）；**OS home 目录内的对象**属确认删除区，需要你显式批准（`dsh-safety allow <id>`），**不许绕行**。
- **冻结区**：`src/core/**` 与 `src/vendors/**` 的 1a 成果已复核冻结，只有计划点名或**记了裁决**的地方才改（本期的裁决依据见 §12 的 ledger）。
- **数值缺失不得当作 0**；写 `visibleModels` 前丢弃空串与纯空白。
- **密钥只进凭据服务**；客户端绝不从设置文档读明文。
